# 08 项目开发流程

> 让 AI 编程从「随缘对话」变成「规范交付」的五步工作流。

## 为什么需要流程

没有流程的典型翻车：一条提示词让 AI 一把梭 → 生成一大坨代码 → 改着改着发现方向错了 → 推倒重来。流程的价值：明确目标、让 AI 准确理解意图、避免失控、做出真正有用的产品。

## 五步工作流

```
需求研究 → 产品需求文档 PRD → 技术设计文档 → AI 指令文件 → 实现与迭代
Research      PRD               Tech Design      AGENTS.md      Build
```

### 步骤一：需求研究（Research）

动手前先回答：做什么？为什么做？有没有人做过？

- 明确目标：解决什么问题、给谁用、做成什么样
- 调研同类产品：看市面上怎么做、优缺点，避免重复造轮子（可以直接问 AI）
- 产出 `RESEARCH.md`：记录目标、调研发现、核心需求清单，不用正式，像写日记

### 步骤二：产品需求文档（PRD）

整个流程中**最重要的一步**。写法：先自己写两三句原始需求，再让 AI 扩展成完整 PRD，最后人工修改确认。

一份 PRD 应包含：产品概述、目标用户、核心功能列表、**功能优先级（MVP vs 后续版本）**、界面设计要求、技术栈建议、边界场景。

关键动作：明确「不做什么」。MVP 功能锁死，其余进「后续版本」，防止范围失控。

### 步骤三：技术设计文档（Tech Design）

回答「怎么做」：技术选型及理由、项目目录结构、数据模型、关键实现思路、接口设计。

让 AI 基于已确认的 PRD 生成技术设计初稿，人工审查——重点看选型是否合理、结构能否支撑后续扩展。

### 步骤四：AI 指令文件（AGENTS.md）

把约束写进项目根目录的 `AGENTS.md`（主流工具通用），内容包括：项目概述、开发规范、代码风格、测试要求、注意事项（如「不要引入新依赖」「修改前先说明方案」）。

这份文件让每轮对话都自动带上项目规矩，是从「口头约定」到「制度化」的关键一步。详见 [[06 上下文管理]]。

### 步骤五：实现与迭代（Build）

- 把 PRD 拆成小任务，**单次对话只做一件事**
- 每完成一个功能：验证 → Git 提交（存档点）→ 下一个
- 出问题回退到上一个存档点，而不是当场硬修（见 [[07 幻觉与死循环处理]]）

## 让 AI 生成更准的实战技巧

- 每轮开工先贴 PRD 对应章节 + 相关文件，再下指令
- 要求 AI「先给方案，确认后再写代码」
- 验收标准写进指令：「完成后运行测试并通过再汇报」

## 反面教材

需求不清的典型对话：「帮我做个网站」→ AI 自由发挥 → 「不是这样的，我要……」→ 反复重做。病根不在 AI，在于跳过了前三步。
